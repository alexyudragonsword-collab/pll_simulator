pllsim v0.9.5 — the six loops compile, and the tolerances say where they came from

Six merged changes above v0.9.4, the last two items of the health-check plan
plus the CI repairs they exposed.  **No stock figure moves.**  The engines
were rewritten and the goldens were compared preset by preset: ILCM, MDLL
and both ADPLL modes are bit-identical to v0.9.4, the three analog loops
differ at the 1e-16 to 1e-9 relative level, and no jitter figure in the
README, this page or the deck changes a digit.

## The per-cycle loops are kernels now

Every engine's loop and every block's per-cycle arithmetic is a module-level
function of scalars and arrays under `core.jit.kernel`.  With
`pip install -e .[fast]` numba compiles each on first use and caches the
machine code; without numba the decorator returns the function unchanged, so
the interpreted path *is the same function* — there is no second
implementation to keep in step.  `PLLSIM_JIT=0` forces Python and
`core.jit.backend()` says which one is running.

Measured on 40k cycles, seed 1:

| run | Python | numba | speed-up |
|---|---|---|---|
| cppll_19p2m_4p8g | 0.39 s | 0.032 s | 12x |
| cppll_frac_38p4m_6g | 0.83 s | 0.039 s | 21x |
| sspll_frac_19p2m_4p806g | 0.73 s | 0.036 s | 21x |
| spll_frac_52m_6p253g | 1.42 s | 0.035 s | 40x |
| adpll_100m_10g / adpll_bb_100m_10g | 0.16 / 0.41 s | 0.023 / 0.034 s | 7x / 12x |
| ilcm_250m_12g / mdll_150m_2p4g | 0.19 / 0.16 s | 0.049 / 0.038 s | 4x |
| cppll, fine_oversample=64 | 122 s | 2.5 s | 49x |
| sspll, fine_oversample=64 | 52 s | 1.0 s | 53x |

The ~25 ms floor is noise synthesis and the FFT post-processing, which is
why the loops that were already cheap gain least.

The plan called for reusing the Android Cython flow.  Cython over the
untyped object code gives ~1.5–2x; the 10–50x needs typed kernels, which in
Cython means either a second implementation or a C compiler on every user's
machine plus a per-platform wheel matrix.  The phone keeps Cython for source
protection and runs the kernels interpreted.

## Bit-identity is a test, not a hope

`tests/test_kernels.py` runs all 18 presets both ways in subprocesses and
requires every record and calibration trace equal to the last bit.  It went
red twice before it went green, and both causes are rules in the
`core/jit.py` docstring now:

- numba's `np.exp`, `x ** 2` and `x ** 0.5` differ from CPython's in the last
  bit (849, 20 and 17 of 20 000 draws); `math.exp`, `x * x` and `math.sqrt`
  do not.  Matrix-vector products go through BLAS, so the 2x2 loops are
  written out.
- Indexing a complex128 array yields a numpy scalar, whose division
  multiplies by a reciprocal where CPython and numba divide.  One bit apart
  at cycle 2195 of 3000 on `spll_frac_52m_6p253g` — found only by logging
  every loop-filter call of the interpreted run and replaying it compiled.

One realization deliberately changes: the BBPD metastability coin is the
sign of the next draw from the pre-drawn pool rather than a uniform, so a
run with `bb_meta_window_s > 0` differs from v0.9.4 after its first
metastable cycle.  No stock preset sets it — the field defaults to 0.0 — so
nothing shipped is affected.

## Where a tolerance came from

About sixty bare bounds in `tests/` now say where the number is from: the
measured value with its seed and run length, or the statistic it is a
multiple of.  Nothing was widened.  Two turned out tighter than they looked
— the ILCM's FTL residual sits at exactly −4 LSB against a 5 LSB bound, and
the SSPLL false-lock test lands on −1.0000 fref to four decimals.
CONTRIBUTING states the convention: a tolerance is algebra, a measurement or
a statistic, and the line should say which.

## What the kernels broke in CI, and what that cost to find

- **Coverage cannot see inside a compiled kernel.**  Installing the `[fast]`
  extra in the coverage job dropped the reported total from 92.4 % to 84.0 %
  and failed the 88 % floor while all 887 tests passed.  CI now runs 3.11
  interpreted with the floor and 3.12 compiled without it; the bit-identity
  test drives both paths in its own subprocesses either way.
- **`abs()` on a complex breaks the Android build and `--host` will not tell
  you.**  Cython lowers it to `cabs()` and includes `<complex.h>` only where
  `_Complex_I` is already defined; glibc's headers do that transitively,
  bionic's do not, so identical generated C compiled green on the host and
  failed the NDK cross build.  The kernels use an explicit
  `sqrt(re*re + im*im)`, the cross compile passes `-include complex.h`, and
  `compile_c` now sets `-Werror=implicit-function-declaration` like the NDK
  does — which does **not** reproduce this case on the host, so `--host` is
  not a full proxy.
- **The mypy gate wants numba and mypy 2.x in the same environment.**  Three
  environments gave three answers about one `njit`-or-None fallback, and only
  CI's was the gate.

## Every branch push was running the suite twice

`ci.yml` answers to both `push` and `pull_request`, and those see different
refs for the same commit, so under `ci-${{ github.ref }}` the two runs landed
in different concurrency groups and neither cancelled the other.  Found by
counting: five Dependabot pull requests recreated at once produced ten runs
in 25 seconds.  The group is keyed on the branch now
(`github.head_ref || github.ref_name`); the obvious
`github.event.pull_request.number` does not work, because that context is
absent on a push.

The main-only example sweep moved to the compiled leg, where it costs 1:44 —
not the "~20 min" its comment had claimed since before the kernels existed.
It never had a `PLLSIM_JIT` of its own, so it had always run compiled on
whichever leg hosted it.

`actions/setup-python` is at 7 and `actions/checkout` at 7.  Both are
verified on the `ci.yml` jobs only; `android.yml`, `release.yml` and
`windows-exe-build.yml` are manual or tag-triggered and no push has
exercised them.

## Corrections

Four comments justified a decision with "a private repo's monthly minute
budget".  The repository is public and Actions minutes are not metered; the
decisions stand on wall clock and runner contention, which is real either
way — a full queue delayed an unrelated job by 17 minutes during this work.

The repository default branch was a working branch rather than `main` until
it was changed during this release.  That is why Dependabot opened its pull
requests against a branch that gets reset onto main, and why every reset made
it recreate all of them.
