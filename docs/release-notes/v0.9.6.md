pllsim v0.9.6 — the picture and the number are the same run

One change above v0.9.5, reported from the field: the MDLL's frequency-domain
and time-domain views disagreed on the APK and the Windows exe.  They did, by
8-11 dB, and the cross-domain sweep had been green throughout — because the
gate and the product were reading different records.

**No stock figure moves.**  `jitter_fs` still integrates the same record it
always did, and the analyze/simulate figures for every preset are unchanged
(MDLL 345.4 / 281.2 fs, ILCM 113.3 / 114.5, CPPLL 258.3 / 236.0).  What moved
is the curve the three front ends draw.

## What was wrong

`plot_pn_breakdown` overlaid `sim.f_psd` — the record sampled once per
reference edge — for all six architectures.  `arch.base.attach_fine` had
already replaced `jitter_fs` from the oversampled record, and said why in its
own docstring: "the oversampled record is the honest one: it contains the
intra-period ripple that the reference-rate record drops."  So one SimResult
reported a number from one record and drew a curve from another.

For an MDLL that gap is not cosmetic.  Edge replacement realigns the
oscillator every reference period, so a record sampled at reference edges
samples the phase exactly where it was just corrected and misses the
intra-period accumulation — which is the architecture's jitter mechanism.
Measured on `mdll_150m_2p4g` over one identical 300 kHz–67 MHz band, same run:

| record | deviation from the model, six bands | jitter |
|---|---|---|
| reference-edge (what was drawn) | −11.5 / −9.3 / −8.6 / −8.0 / −7.7 / −7.0 dB | 128.6 fs vs model 303.6 |
| oversampled (what was reported) | −3.2 / −2.0 / −2.1 / −1.8 / −1.9 / −1.8 dB | 244.9 fs vs model 303.6 |

The ILCM reads 0.1 dB on the reference-edge record, which is why this looked
like an MDLL problem rather than a record problem.

## Why the sweep stayed green

It was reading the other record.  The grid named `psd_source="fine"` for the
MDLL points by hand, with no comment saying why.  The gate and the product
each stayed correct about a different question, so neither went red — the
failure mode this project has been bitten by before, in a new place.

`SimResult.reported_psd` is now the single answer to "which record does this
result report".  `plot_pn_breakdown` and `compare_domains` both defer to it,
and the grid's per-point overrides are gone.  No page in `webgui`, `guiqt` or
`appbridge` touches a PSD array directly — checked by search — so one call
site covers all three surfaces.

## A gap that would have been noise

Routing the comparator to the oversampled record put `ilcm-fref-x2.0` at
2.37 dB over a 2.0 dB base with no boundary flag, which the sweep's own rule
calls a model defect.  It was not one.  That band held 32 points of a single
full-length periodogram, about 5.6 dB of spread per bin; across seeds 1–5 it
read +2.37, +1.56, +1.22, −0.50 and +1.97 dB.

`attach_fine` now keeps a Welch estimate of the same trace beside the
periodogram — frequency resolution for the spur table, segment averaging for
the comparison, which is the variance the tolerances were calibrated against.
The worst-band spread over those same five seeds fell from 2.87 dB to
0.73 dB.  Pinning the 2.37 as a gap, or widening the ILCM's base tolerance,
would each have recorded a realization as physics.

## Still true, and not fixed by this

The MDLL's two headline jitter figures still differ: 345.4 fs from the linear
model, 281.2 fs from the time domain.  They cover different bands — the model
integrates the full `int_band`, `simulate()` stops at 0.45·fref — which is the
declared `jitter-band-clip` boundary, noted at runtime on all three surfaces.
Reading the curve is now the way to compare the two; reading those two numbers
against each other is not.

offscreen 62 (under `PLLSIM_CI=1`, so a missing optional dependency fails
instead of skipping), Android bridge and parity 80, all 21 examples, and the
phone page driven in real Chromium — its cursor reads 7 curves within 0.01 dB
of `analyze()`.  ruff clean, mypy clean on 93 files, docs consistency 26.

`tests/test_psd_record_shown.py` was written red first: 3 of its 5 failed
before the fix, the MDLL one reading "integrating the drawn curve gives
128.4 fs but the result reports 281.9 fs".  One of the five is a textual guard
that the sweep grid never names a record again, because the defect was the
second opinion rather than a wrong number.
