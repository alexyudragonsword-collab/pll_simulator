Everything a completeness audit of v0.9.0 turned up.  Each finding was
reproduced numerically first -- driving the parameter and watching nothing
happen -- rather than inferred from reading code.

## Numbers that changed

Integrated jitter is unchanged for every preset.  Two things move:

| quantity | v0.9.0 | v0.9.1 | why |
|---|---|---|---|
| TDC-INL spur, `adpll_100m_10g` @ 600 kHz | -24.18 dBc | -28.18 dBc | the loop walks 78% of the code range, not all of it |
| its harmonics @ 1.2 / 1.8 MHz | not predicted | -48.9 / -58.4 dBc | a fractional cycle count spreads over every k |

The time domain measured -28.49 / -46.45 / -56.73 dBc throughout.  It was
right all along; nothing had compared the two.

## The corner supply axis was a label

Every standard corner names a supply -- `SS_125C_0.9V` -- and nothing in the
model ever read it.  Sweeping `Corner.vdd` from 0.5 to 2.0 left the jitter at
258.3043 fs, to four decimals, at every point.

It now acts through the oscillator's own `pushing_hz_v`.  That is the only
honest route: an oscillator states how many Hz it moves per volt and a corner
states a *relative* supply, so the two need a nominal in volts to meet, which
is the new `Corner.vdd_nominal_v`.  A preset that has not characterised
pushing comes back untouched rather than having a sensitivity invented for it.

## apply_corner returned an alias

It rebuilt only the sub-configs its corner happened to scale.  At TT -- which
scales nothing, and which `corner_report` runs *first* -- the returned PLL
shared its whole config object with the nominal, so anything downstream that
edited it corrupted the baseline for every later corner.

The existing test for this passed only because it used `SS_HOT` (which does
rebuild things) and compared scalars rather than object identity.  The new one
is parametrized over TT as well and walks the whole config tree.

## Which variable is the INL a function of?

`TDCConfig` declares the INL shape over the converter's *code range*.  The
loop only ever walks one oscillator period of it -- and a TDC is deliberately
built with range > Tosc, here 78% of the axis.  So a shape declared as three
whole cycles across the range presents 3 x 0.78 = 2.34 cycles to the loop.

A fractional cycle count is discontinuous at the wrap, and the wrap is what
radiates: the declared line drops and the energy reappears at every other k.
Ignoring the span overstated the worst spur by 4.3 dB and missed the harmonics
entirely.

`tdc_inl_spur_table` now takes the `TDCConfig` rather than the INL tuple,
because the resolution and bit count are what set how much of the shape the
loop sees -- they are not optional.  The table trims to 40 dB of dynamic
range, since spreading one declared cycle over sixteen harmonics would
otherwise bury the two lines that are findings under a dozen at -110 dBc.

## The intra-period drive, solved rather than stepped

Intra-period sampling is what makes the reference spur visible at all.
`drive_fine` was stepping the loop filter M times per reference cycle in
Python: 73% of a spur run's time, and the reason M was quietly kept small when
resolving a 200 ps reset pulse inside a 52 ns period needs a few hundred.

The system is LTI and diagonal in its eigenbasis, so every sample time has a
closed form.  Evaluated for all M at once: **7.8x faster at M = 512** (19.0 s
-> 2.4 s on a 3000-cycle run), bit-for-bit identical at every M tested.

The subtlety worth recording: the exponents must be of *clipped elapsed* time.
The algebraically equivalent `e^{wt}(e^{-wa} - e^{-wb})/w` overflows for a
fast pole, because `e^{-w*tstep}` is the reciprocal of a number the stable
dynamics have already made tiny.  The type-II integrator sits exactly at
w = 0, so that branch is the elapsed duration plus one correction term -- and
only one, because at the 1e-8 switch point the next lands at 1e-17, under the
double-precision floor where no test could tell it from nothing.

## Both GUIs expose M

With the two things that go wrong printed next to it: a sub-interval coarser
than `cp.t_reset` reads the spur *low*, and the record is M floats per
reference cycle -- 600 MB at 150k cycles and M = 512.

`0` means "leave the engine default", which is not `1`: ILCM and MDLL default
to 4 because their jitter figure is defined inside the period, and forcing 1
would silently redefine what they report.

## Documentation that states a fact about the code is code

The README's numbers had drifted twice -- 150 tests, then 204, against a suite
well past both.  It still listed a `blocks/divider` deleted two releases
earlier and had never listed `corners.py`, `tdcspurs.py` or `lockdetect.py` at
all.  `docs/index.html` said five architectures in one place and six in
another, and 13 presets where `ALL_PRESETS` holds 15.

It also carried a claim that had been false since v0.7.0: that reference-rate
simulation cannot show spurs at >= fref/2.  It can, with `fine_oversample`, to
0.02 dB against the analytic model.

`tests/test_docs_consistency.py` checks the stated counts against
`ALL_PRESETS`, `sweepable_presets()`, the `arch/` package, the example
directory and a live pytest collection, and checks the repository-layout block
in both directions -- a module that is missing and a module that no longer
exists both fail.  Mutation tests confirm each check fails when the README is
wrong.

The test count is checked against a band rather than for equality.  A hard
equality fails on every PR that adds a test, which trains people to edit the
number without reading it; a band still catches the 2x drift that actually
happened.

## Also

- `pllsim.corners` raised `AttributeError` while `pllsim.presets` worked, with
  nothing to tell a user which sibling needs its own import.  The analysis
  modules are now imported by the package.
- `pllsim.__version__` against `pyproject` is now a test.  A stale editable
  install is not a code bug, but every number a run stamps into a report
  carries it, and this is how you find out to reinstall.
- Deleted `tr_items()`, which had zero callers.
- **ex21**: corners across all six architectures without retuning, the supply
  axis on its own, lock-detector traces (including a window near the loop's
  own error, which asserts once and falls out), and pulling vs offset against
  Adler.  5 s, so it joins the fast CI subset.

## Tests

405 -> 437.  Every P0 fix has a regression test confirmed to fail on the
pre-fix code.  The `drive_fine` closed form is checked against stepping with
the already-trusted constant-current update, and mutation tests pin the clip,
the amplitude and the series coefficient.
