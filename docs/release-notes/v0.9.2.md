pllsim v0.9.2 — the deck that went stale, the spur page that could not show the reference spur, and a type checker's first run

No modelling numbers change in this release.  Three findings from checking
what v0.9.1 had actually left open.

## The deck went stale one release after the documentation test landed

`pllsim-项目总结-v0.9.0.pptx` still claimed 405 tests and 20 examples.  It is
a binary, so nothing diffs it, and every number in it had been typed by hand
-- while its own README said that a binary with no source only goes quietly
out of date.  That is precisely what happened *inside* it.

`collect_facts.py` now emits the counts, the version, the release count and
the benchmark table; `build_deck.js` reads them and refuses to run without a
`facts.json`.  Three tests check that the shipped `.pptx` was rebuilt from a
current one rather than merely that the generator exists, and a fourth pins
the benchmark rows to `presets.benchmark_table()`.

That fourth one is the case worth naming: the deck's README claimed those rows
came from `benchmark_table()` and they did not -- they were five hardcoded
rows that happened to still be right.

## The page named "spur prediction" could not show the reference spur

It became measurable in v0.7.0 and reachable from the workbench in v0.9.1, but
the spur page in *both* GUIs still did fractional spurs only: the reference
one lives inside a single reference period and the page ran the default
once-per-edge `simulate()`.

Both now carry an M control and an analytic-vs-time-domain table.

| preset | analytic | measured |
|---|---|---|
| `cppll_frac_38p4m_6g` (3% mismatch) | -103.2 dBc | -103.3 dBc |
| `sspll_frac_19p2m_4p806g` | - | - |
| `adpll_bb_100m_10g` | no intra-period record | |

The blanks are answers, not gaps.  A sub-sampling loop's gm converts the held
voltage over the same window the loop cancels it in, so in lock it delivers no
charge at all -- the row reads "-" with that sentence beside it.  ADPLL says
it has no analog control node: its control word is a register that changes
once per reference edge and holds, so there is no intra-period waveform to
sample.  That is the architecture, not a gap, and `supports_fine()` now says
so in its docstring.

### Adding a button broke a test into passing for the wrong reason

The Streamlit tests pressed buttons by *position*.  The new reference-spur
button landed third, so the channel-sweep test went on passing while pressing
it -- helped by an `or out.dataframe` escape hatch wide enough to accept
anything the page rendered.

Every button on that page now carries a key, the tests select by key, and the
escape hatch is gone.  Verified by pointing the test at the wrong button and
watching it fail, which it had not done before.

## A type checker ran on this codebase for the first time: 115 errors

Most are `Optional` narrowing the engines guard at runtime but a checker
cannot see through.  So the gate covers what it can actually hold today --
`core/`, `blocks/`, `calibration/`, `arch/base.py` and the analysis modules,
i.e. everything whose types carry a *convention*: rad^2/Hz vs dBc/Hz, seconds
vs UI, amps vs coulombs.  29 files, clean.

`arch/` and `webgui/pages/` are listed in `pyproject.toml` as **not yet
covered** rather than silenced with a blanket ignore.  An exclusion list that
says what is missing is honest; `ignore_errors` on the whole package would
read as "type-checked".

Of the errors it did fix, the one worth keeping is structural: `PLLBase` never
declared `cfg`, though corners, Monte Carlo, the selector and both GUIs all
reach for it -- a contract six subclasses happened to share.

One trap, recorded because it cost a CI round: mypy parses installed stubs
against the version it is *configured* with, not the one it runs on.  Pinning
`python_version = "3.11"` made the 3.12 job fail inside numpy's own `.pyi`
("type statement is only supported in Python 3.12 and greater") before
reaching any project code.  Following the running interpreter is what a
version matrix is for.

## Coverage gained a floor, and three pages became testable

Floor at 88%, measured 91%.

The three dynamics pages sat at **47%** because their entire computation lived
in a closure inside the click handler, unreachable from a test without driving
the thread pool -- and "the button raises the moment it is pressed" is the
failure this GUI has actually had.  They now have named `compute()`/`render()`
pairs, like the workbench already did, and sit at **95%**; the tests call
exactly what the worker thread calls.

Two things the coverage number does not say, both written next to it in
`pyproject.toml` and the README.  The Streamlit pages are driven by 23 tests
through `AppTest`, which execs each file rather than importing it, so coverage
attributes none of it and `webgui/Home.py` reads 0% while its test passes --
do not "fix" that with a test that merely imports it.  And a covered line is a
line that ran, not a line whose answer was checked; the physics is pinned by
cross-domain comparison, not by that percentage.
